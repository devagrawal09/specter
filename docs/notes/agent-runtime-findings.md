# agent-runtime findings log

Specter rough edges and decisions discovered while building `apps/agent-runtime`. One entry per finding; newest last.

## 2026-10-08 — scaffold (M1 task 1-2)

- **`@ocpp/schema` must be linked, not `file:`-installed.** Its `package.json` uses `catalog:` dependencies, which pnpm cannot resolve from a `file:` copy. `link:../../../opencode/packages/schema` works; its `exports` map points at `src/*.ts` so no tsconfig `paths` were needed.
- **Effect version skew is a type-level problem, not a runtime one.** `@ocpp/schema` resolves `effect@4.0.0-rc.112` from OC++'s `node_modules`; Specter is on `4.0.1`, which renamed `Schema.isStartsWith` -> `isStartingWith`. OC++'s schemas do not compile against 4.0.1, so `src/events.ts` casts before `Schema.toStandardSchemaV1`. Runtime decode/validation works (smoke-tested). Cost: `sessionEventDefinitions` loses typed payloads until the versions align (M2 prerequisite: bump OC++ to 4.0.1 or vendor the schema build).
- **49 durable session events, not ~45.** `SessionEvent.DurableDefinitions` has 48 public plus the internal `UsageRecorded`.
- **Specter exporter fails on zero specs.** `spec export` errors with "No spec.ts files matched" for an app with no slices yet; the app's `spec:build` guards with `ls`. Candidate Specter fix: exit 0 with a notice.
- **Base tsconfig pulls `packages/core/src` via `paths`, so the app needs the DOM lib** (`TextEncoder`, `AbortSignal`). A UI-less app should not need DOM; candidate Specter fix: core should type against `lib.es2022` + node types only.
- **`paths` overrides rather than merges**, so every app repeats the `@specter-ts/core` entries.

## 2026-10-08 — first specs (M1 task 3-4; 33 scenarios across 3 slices)

- **Dotted event types are rejected by the normative spec format** (`packages/spec/src/validation.ts:165`, `specification/schemas/slice.schema.json`). Decision: keep Specter kebab-only; the app maps `.` -> `-` in `src/events.ts` and the M4 bridge maps back.
- **No no-op scenario outcome.** A scenario must `expect` at least one Event or `reject` (`validation.ts:137`, schema `expect minItems: 1`). OC++'s idempotent admission ("first admission wins; retried payload ignored") and post-delivery retry reconciliation are therefore inexpressible, even though Specter's runtime has first-write-wins idempotency as the default mode (#48). Candidate Specter change: allow `expect: []` without `reject` meaning "accepted, no new facts".
- **The spec builder has no `.inputSchema` / `.outputSchema`**; only `.description().scenarios()`. Input/output shapes are implied by scenario payloads. The runtime builder has them (runtime.md "Schema modes"); the authoring package does not.
- **`event()` payloads are untyped `JsonValue`** and are not checked against the app's event definitions at export time. "Same payloads as OC++" is enforced only at runtime, not in `spec.ts`. Candidate Specter change: `spec export` validates `given`/`expect` payloads against the registered definitions when available.
- **Cross-aggregate reads in `given`.** The enqueue-input cross-session rejection scenario puts another session's events in `given`, assuming the Command can see them. This is the cross-aggregate read the plan flagged; it will be settled when the impl is written.
- **Exact rejection reasons are invented.** session.md names error types (`LifecycleConflict`, `SessionNotFoundError`) but no messages; the specs use short sentences. Align with OC++'s error schemas before M4.
- **No-op outcome — decided 2026-10-08:** keep Specter's rule. Idempotent retry is a rejection in the app (exact reason), translated back to OC++'s silent success at the M4 facade. Revisit if a second app needs "accepted, no facts".

## 2026-10-08 — first implementation (M1; 3 slices, 36 scenarios)

- **Effect skew breaks runtime decode, not only types.** Mixing `@ocpp/schema` (effect rc.112) with Specter (4.0.1) throws `s.startsWith is not a function` for every payload. Tests alias `effect` to rc.112 in `vitest.config.ts`; Specter core runs fine on rc.112. Must be resolved before M2 (align versions), and the earlier "type-level only" note was wrong.
- **Spec payloads are not validated against event schemas at `spec:build`.** Both spec writers used `inb_*` inbox IDs and `{type:'local'}` locations; `@ocpp/schema` requires `msg_*` and `{directory}`. Nothing caught it until the conformance check at test time. Strong case for the exporter validating `given`/`expect` payloads when definitions are available.
- **Conformance `extra-apply-handler` forbids apply handlers for events that never appear in a Given.** Reasonable as a lint, but it forced dropping the `session-inbox-cancelled` apply until a duplicate-cancel scenario was added. Rule should probably be a warning, or apply handlers should count as covered when the slice emits that event.
- **`eventsFor(slice, catalog)` is required for per-slice tests**; a whole-app catalog fails conformance with `event-without-scenario` for every unmentioned event. Fine, but undocumented for multi-slice apps with large catalogs.
- **Query builder: `.outputSchema<T>()` must precede `.store`**, and omitting it yields a type error that does not say so.
- **Slice state is projected from the global log**, so per-session state is keyed manually by session ID inside each slice. Cross-aggregate reads in a Command therefore work (the cross-session inbox-ID rejection scenario passes) — the plan's open question is answered: yes, trivially, because there is no aggregate boundary in slice projections.
- **Harness throws on `[]` from a Command** ("Command emitted no events"), consistent with the spec-format rule; the app models idempotent retry as a rejection (decided).
- **Correction: the no-op restriction applies to Commands only.** Reaction scenarios accept `expect: []` ("requests nothing"), as in `apps/reference`'s cheer reaction. So "repeated wakes coalesce" is directly expressible as a Reaction scenario; only Command-level idempotent success remains inexpressible (modelled as rejection, decided).

## 2026-10-08 — execution lifecycle (M1; 5 more slices, 75 scenarios)

- **Reaction handlers receive slice state only, never the triggering event.** First implementation stored a transient `wakeFor` in state and had every other event clear it — a smell. The Specter idiom is state-derived requests ("any session with pending input and no active execution -> request startExecution"), which is idempotent and makes wake coalescing fall out. Refactored accordingly. Documentation should say this explicitly: Reactions are projections that decide from state, not event handlers.
- **`resume: false` is not a durable fact in OC++ either** (the inbox item schema has no field; session.md: "resume controls scheduling, not durability"). A state-derived wake Reaction cannot honor it without an app-defined fact. Deferred to M2: candidates are an app-level `session-inbox-held` event, or letting the facade own it (but the facade cannot stop a Reaction).
- **Apply-handler conformance lints cut both ways.** `missing-apply-handler` demands a no-op `.apply` for any Given event the slice ignores (interrupt-execution needed one for `session-inbox-enqueued` precisely to prove "interrupt does not touch input"); `extra-apply-handler` forbids handlers for events never in a Given. Both should probably be warnings, and ignoring an event should be expressible without a handler.
- **Reaction `outputSchema` accepts any Standard Schema** (Effect Schema used; no Zod). Undocumented.
- **Undocumented: whether the Reaction harness evaluates after each Given event or only after the last.** Scenarios here pass either way; the semantics matter for request-count assertions.
- **One Reaction commit produces zero or one output** (`plugins.md` Invariants; `handle(state) => Promise<TResult | undefined>`). A state-derived Reaction that needs to act on several aggregates must rely on its own output's commit re-running it (wake ses_1 -> started commit -> wake ses_2). Works, but is a hidden serialization; worth documenting as the intended pattern or allowing arrays.
- **Interrupt must not re-wake.** With only { pending, active } a state-derived wake would restart a session the user just interrupted (input is still pending). An `interrupted` flag derived from `session-execution-interrupted`, cleared by the next enqueue/start, matches OC++ ("interruption stops execution without deleting pending input"; only a new enqueue or explicit resume wakes).

## 2026-10-08 — step loop with a scripted model (M1; 4 more slices, 44 scenarios + 3 integration cases)

- **Slices cannot import sibling Slices (`scripts/check-slice-imports.mjs`), but a Plugin's `query(slice, input)` needs the Query Slice value.** The outboxed step Plugin lives in `src/plugins/run-step.ts`; `createRunStep(plugin)` takes it as a parameter and `src/app.ts` composes `withReactionOutbox(plugin, { store })`. Worth documenting as the intended pattern for Plugins that read Queries.
- **Reaction requests derived from state duplicate under one-output-per-commit.** With two Sessions active, a commit for ses_2 re-requests ses_1 (lowest eligible), and `step-ended` queues the next request before the current job has dispatched `finishExecution`, so a stale job follows a settled execution. Fix used: the request carries `ordinal` (steps started); the Plugin's first act is `query(stepStatus)` and it drops requests that are inactive, in flight, or whose ordinal is stale. The Command rejections (`Execution not active`, `Step already started`) are the safety net; the Plugin treats `SpecterCommandRejectedError` as "world moved on" and stops.
- **Dist bundles of `@specter-ts/memory` and `@specter-ts/reaction-outbox` inline their own `effect` 4.0.1** (vite does not externalize it; `succeedWith` appears in their `dist/index.js`). Under the rc.112 alias this fails with `t.succeedWith is not a function`. `vitest.config.ts` aliases both packages to `src/index.ts`. Independent of the OC++ skew: two Effect copies in one process is a bug for any consumer.
- **Whole-app conformance rejects a registered catalog with unported events** (`event-without-scenario` x40). The integration test registers `eventsFor(slice, catalog)` unioned over the registered Slices. A host app would need the same; consider a documented "partial catalog" mode.
- **No test harness for outboxed Plugins.** The integration test drives the real app and polls (`waitFor`) the memory Event Log and `outbox.list()` for `completed`; the worker is a background poller with no `drain`/`idle` handle reachable from the app, so tests need timeouts. A `settled()` on the outbox plugin (or a manual-drain option) would make this deterministic.
- **Query at the step boundary reads committed state.** `query` inside the outboxed Plugin worked in all three cases (no `SPECTER_PLUGIN_QUERY_IN_TRANSACTION`). Remaining race, not closable by Specter today: `deliverInboxItem` has no execution-active precondition, so a stale job could deliver one item after an interrupt between its status check and the Command. The Plugin narrows it by checking status first; the Command could own the check once cross-slice preconditions are expressible.
- **Crash between `step-started` and `step-ended`** leaves the step in flight: the outbox retry sees `stepInFlight` and drops the job. Needs an attempt/retry story (session.md "Physical Attempts") in M3.
- **`recordStepStarted` runs before the model call**, not after: a step is in flight while the provider streams, which is what lets interrupt-mid-step be tested and matches session.md.

A directory target (`./node_modules/effect`) silently fails to apply because effect is an `exports`-only package and TypeScript's `paths` directory resolution does not read `exports`.

## 2026-10-08 — delivery precondition

- **Race closed at the Command.** `deliverInboxItem` had no execution-active precondition, so a stale outboxed step job could deliver one item after the user interrupted, between the Plugin's `stepStatus` check and its Command. In OC++ delivery is runner-owned and impossible without an active execution.
- **Fix:** the slice's private projection now folds `session-execution-started/succeeded/failed/interrupted` into an `active` flag and rejects `Execution not active` right after the Session check. Specter serializes the Command, so the check is race-free; the Plugin's existing `SpecterCommandRejectedError` handling treats it as "world moved on".
- Scenarios: +4 (never started; started then interrupted/succeeded/failed — the settled-event scenarios are also what conformance needs to allow their apply handlers). All other scenarios that reach the item checks now carry `session-execution-started` in Given.

## 2026-10-08 — retries

- **Added `record-step-failed` (11 scenarios) and `schedule-retry` (15), extended `step-status-query` (+6, `attempts`/`lastFailure`), `run-step-reaction` (+5), `record-step-started` (+4).** A retried step is the same step: `session-step-started` repeats the `assistantMessageID` after `session-retry-scheduled`; the scheduled retry is the only thing that re-opens a step id.
- **Constraint broken on purpose: `record-step-started/spec.ts` was extended.** Reusing a step id needs `record-step-started` to fold `session-step-failed`/`session-retry-scheduled`, and conformance (`extra-apply-handler`) refuses apply handlers whose event never appears in a Given. No way to change a Slice's lifecycle without touching its spec.
- **Every lifecycle change fans out to every Slice that duplicated the lifecycle projection.** Adding "failed" touched five projections (started, failed, retry, run-step, step-status). `record-step-ended` and `finish-execution` were left alone, so `record-step-ended` still lets a *failed* step be "ended" (its status stays `started`). Fixing that means touching its spec too. The duplicate-don't-share rule is cheap per Slice but the cost lands here; a shared step-lifecycle fold may now be a "real shared boundary".
- **`schedule-retry` derives the error from state** (the latest `step-failed`) instead of taking it as input; the caller cannot misreport it. Attempt number = scheduled retries + 1; budget is the `limit` input (default 3). Retry classification (which failures are generic/transport) lives in the Plugin/model adapter; the Command only owns the budget.
- **Reaction request for the retry is identical to the first** (`{sessionID, ordinal}` with the same ordinal). The outbox did not dedupe it (the run succeeded), but that relies on outbox keys including the delivery/commit, not payload equality. The stale-request guard in the Plugin now needs the failure marker (`lastFailure`) to tell "retry of ordinal N" from "next step N+1".
- **A rejected `scheduleRetry` is read as "no retry"** in the Plugin (limit reached, or world moved on) and falls through to `finishExecution` with the error. `SpecterCommandRejectedError` does not carry a typed reason, so the Plugin cannot distinguish `Retry limit reached` from `Execution not active` without string matching; it relies on the follow-up `finishExecution` being rejected too.
- **Not expressed from session.md:** jittered exponential backoff and honouring a provider retry delay (`at` is recorded as `Date.now()` and not waited on); the budget of "initial + four retries" (default here is 3 per the task); incomplete-stream-after-durable-output continuation with a new assistant message ID; provider continuation rejection rebuild; content-filter finish as a step failure (the Command accepts `finish: 'content-filter'` but no Plugin path emits it); "later activity clears projected retry state" is only partly modelled (`lastFailure` clears on the next attempt or terminal event).

## 2026-10-08 — crash, restart, fork (M3; 2 slices, 31 scenarios, 2 recovery tests, JSONL composition)

- **Compositions.** `src/app.jsonl.ts` `openJsonlSessionApp({ directory, model, outbox? })` composes the same Slices and step Plugin over `events.jsonl`, `outbox.jsonl` and `slices/*.json` in one directory; the memory composition stays for scenario tests. To share the Slice list, `app.ts` gained `createSliceStoreLayer(provide)` (memory and JSONL each pass their per-store provider; an array-and-cast version lost the Layer's typed requirements) and `createSessionAppConfig(outbox, outboxOptions)` so worker tuning (`leaseMs`, `heartbeatMs`, backoff, `shutdownTimeoutMs`) reaches `withReactionOutbox`.
- **Restart needed no resume code in the app.** Opening the same directory is enough: the Event Log and outbox take over the dead process's locks (`recoveredStaleLock.pid` is the killed child), the outbox makes the attempt it left running claimable at once (`releasedOnOpen: ['runStep:3']`), the worker re-runs the job, and Slice cursors catch up from the log. The only app change was in the Plugin: what to do when the resumed job finds its step in flight.
- **JSONL `releasedOnOpen` makes lease expiry irrelevant on restart.** The JSONL outbox releases every attempt a previous open left running at open time, not after `leaseMs`. `leaseMs`/`heartbeatMs` therefore only matter for a stalled-but-alive worker, which a single-writer JSONL Store cannot have; expiry-based reclaim is untested here. The child ran with `leaseMs: 300` and the job journal grew one `renewed` line per ~100 ms for the life of the attempt (default 5 min lease: one line per 100 s, still unbounded for a long step). Worth a note in the README, or a compaction.
- **Unclean death cannot be simulated in-process with JSONL.** A second open of `events.jsonl` in the same process throws ("already open in this process") and a live pid's lock is never taken over, so "abandon app A" in-process either leaves A's worker running or needs the shutdown path. The test spawns a real child (`src/recovery.child.ts`) and SIGKILLs it. Node child plumbing cost three things: (1) `tsx` + the app tsconfig applies `paths` that point `effect` at `.d.ts` files (`TSX_TSCONFIG_PATH=/dev/null` fixes it); (2) `--preserve-symlinks` (the Node twin of vitest `dedupe`) breaks pnpm's layout for tsx's own `esbuild`, so `src/single-effect.mjs` registers a resolve hook sending every `effect` import to the app's copy; (3) the packages' `dist` had to be built (`packages/jsonl/dist` had only `.d.ts` files). Candidate Specter helper: a documented crash-harness fixture for apps (the jsonl package has one, `lock-child.fixture.ts`, but it is package-private).
- **Dependency plumbing.** The app now depends on `@specter-ts/jsonl`, `tsx` and `@types/node` (the first Node-API code in the app; tsconfig `types` gained `node`). `pnpm install` refused to run (`ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`: it wants to purge `node_modules`), so the lockfile was updated with `pnpm install --lockfile-only --offline` and the three workspace/store links were created by hand; a clean checkout's `pnpm install` is untested. Because that check also fires before every `pnpm run`, `pnpm check/test/typecheck` here were run with `--config.verify-deps-before-run=false`.
- **The outbox does not tell the handler its job was claimed before.** The wrapper calls `execute(delivery.output, delivery.context)`; the worker's `ReactionOutboxAttemptContext` (`attemptNumber`, `attemptId`, `jobId`) is dropped at `handle: (delivery) => ...`. The handler sees only core's `ReactionDeliveryContext` (`deliveryId`, `scheduledAt`, ...). Used the slice state instead. Candidate Specter change: pass the attempt context (at least `attemptNumber`) to outboxed Plugins.
- **Orphan reconciliation design.** `stepStatus` gained `inFlightStepID` (3 scenarios amended). At job start, `active && stepInFlight && request.ordinal === stepsStarted - 1` means the step belongs to a dead attempt, because the worker runs one job at a time and a live handler would not have been re-claimed. The Plugin then (1) `recordStepFailed { error: { type: 'orphaned', message } }` (`SessionError.Error` is `{ type: string, message: string, status? }`; any `type` conforms), (2) `scheduleRetry`, or `finishExecution` with the same error when the budget is spent, and returns without calling the model. The retry fact makes the Reaction request a fresh job (new `deliveryId`), which runs the normal path and starts the next physical attempt of the same `assistantMessageID`. No Command precondition changed; no new Command. The resume therefore relies on the one-worker-per-Store invariant (README: a worker claims every job in its Store).
- **Idempotency keys are why reconciliation must end the job.** Plugin commands use `${deliveryId}:started` etc. A resumed job has the *same* `deliveryId`, so re-running `recordStepStarted` under it would be deduplicated by the Event Log into A's commit and no new `session-step-started` would appear. Starting the new attempt from a new Reaction request (new `deliveryId`) is what makes the keys distinct.
- **Known gaps.** (a) A crash after `recordStepFailed` and before `scheduleRetry` (in reconciliation, and equally in the ordinary retry path) leaves the execution active with a failed step and no request; the resumed job sees no step in flight and falls through to `recordStepStarted` with the old step id, which is rejected. Closing it needs `awaitingRetry` (and retryability) exposed by `stepStatus`, or one Command emitting `step-failed` + `retry-scheduled` in a single commit. Not done. (b) The model call is repeated after a crash; no exactly-once (matches session.md). (c) The write-ahead execution claim is the outbox lease plus `session-execution-started`; no separate claim fact and no "recovery attempts per claimed execution" counter beyond the retry budget (orphan retries share it: after 3 orphaned attempts the 4th open fails the execution; tested). (d) Session.md's "append a durable continuation instruction" on recovery is not modelled; instructions are not ported.
- **Fork as a projection.** `fork-session` (Command, 16 scenarios) emits `session-forked { sessionID: child, parentID, boundary }`; `session-history-query` (Query, 15 scenarios) returns a Session's history as ordered `{ messageID, sessionID (recorder), type: user|synthetic|assistant, status? }`. Both fold `session-forked` by copying the parent's history up to the boundary at that moment (frozen copy, as OC++'s projector copies rows), so there is no recursion at read time and no Event Log fork. History = delivered inbox items plus assistant messages (first `step-started`; a retried step stays one message). Rejections: unknown child/parent, boundary not in the parent's history (pending items are not history), child already forked or with own history, self/ancestor cycle. Fork of a fork works because the middle Session's copy is what the boundary is checked against. Both slices duplicate the history fold on purpose.
- **Not expressed from session.md for fork:** the child adopting the parent's newest instruction values (`instructions`, `instructionEntries` on `session.forked` are omitted; instructions are not ported); `RequestBoundary` (`through` without a message ID = the parent's latest) is a facade concern; session creation of the child is assumed to have happened (`session-created` for `ses_2` is a precondition; there is no create-session slice yet); title/metadata inheritance. **Revert (stage/clear/commit) is out of scope for this task** and still open for M3.
- **Spec tooling.** Every spec file must `export default` its spec or `spec:build` fails with "must default-export exactly one Slice specification" (and then every `impl.ts` fails to find `spec.json`, a confusing cascade of TS2307 errors). The no-op `.apply` lint rules (see earlier entry) applied again: the Command needs a no-op `inbox-enqueued` handler only because a Given uses it for realism.
- **The existing "crash between step-started and step-ended leaves the step in flight" finding is closed** by reconciliation; the "needs an attempt/retry story" part is now the orphan failure plus retry budget.

## 2026-10-08 — atomic failure outcome

- **The hole:** step failure was two commits (`recordStepFailed`, then `scheduleRetry` or `finishExecution`). A crash between them left `session-step-failed` with no retry and no failed execution, and the state-derived run-step Reaction requested nothing: stuck forever, in the ordinary retry path and in orphan reconciliation alike.
- **The fix:** `record-step-failed` owns the whole outcome (input `retryable`, `limit` default 3, `at`) and emits `session-step-failed` plus exactly one of `session-retry-scheduled` (retryable, budget left) or `session-execution-failed`, in one commit. `schedule-retry` (15 scenarios) is removed, and `finish-execution` drops its failure path (2 scenarios) so it only succeeds. The Plugin dispatches one Command per failure.
- **Easy/hard:** the one-owner rule made the fix a deletion; run-step-reaction and step-status-query folds already handled both events in one commit, so they needed no change. Multi-event commits are a first-class `expect` list. Hard: the retry budget count moved into the failure Command's duplicated projection, and the Plugin still cannot tell which rejection it got, but now a rejection only ever means "world moved on". Closes known gap (a) in "crash, restart, fork".
- **`resume: false` — deferred (2026-10-08).** `git grep` across OC++ `v2` finds zero callers in source or tests; only `packages/protocol` declares it (`Schema.Boolean.pipe(Schema.optional)` on prompt/command/synthetic). Not modelled; the wake Reaction stays purely state-derived.

## 2026-10-08 — revert

- **Slices (53 new scenarios, 253 tests total):** `stage-revert` (13), `clear-revert` (10), `commit-revert` (10), `revert-status-query` (7, `{ staged: Revert | null }`; a separate Query because a field on `execution-status-query` would have rewritten every existing scenario's expected output). Amended: `session-history-query` (+9), `fork-session` (+3), `enqueue-input` (+1, no-op apply).
- **Oracle derivation.** `revert.ts` `commit` publishes `session.revert.committed { sessionID, to: session.revert.messageID }` and returns silently when nothing is staged (Specter: rejection "No revert staged"). `stage` publishes `session.revert.staged { sessionID, revert: { messageID, snapshot, files } }` and replaces any previous staged revert (it reuses the original snapshot), so stage never rejects "already staged". `clear` is a silent no-op when nothing is staged (rejection here, as with interrupt on idle). The protocol lists `SessionBusyError` for all three endpoints, so clear rejects "Session is busy" too.
- **History rule.** A committed revert ends the Session's history at `to`, inclusive (`plan` selects assistant messages with `seq > boundary`, so the boundary stays). Projection only: the Event Log is untouched. A staged revert changes nothing. Pending inbox items are untouched (`revert.ts` says nothing about them); one enqueued before a commit is still delivered into the reverted history afterwards.   - Runtime, in OC++: the linked app resolves effect from Specter's `node_modules`. A Bun preload plugin (`onLoad` on files under the runtime's effect directory) re-exports OC++'s copy. Bun's runtime `onResolve` never sees bare package imports, so it cannot redirect them; `onLoad` must return contents, so its filter matches only the foreign copy. Without the plugin, schema validation across the boundary crashes (`s.startsWith is not a function`), and the smoke test catches it.

Rule: OC++ imports only `@specter/agent-runtime`, and the app maps `@specter-ts/core/effect` to source like the other core entries. Its index re-exports `SpecterCommandRejectedError` so `instanceof` works in OC++.

The app is registered once per machine (`bun link` in `apps/agent-runtime`), and OC++ core depends on `link:@specter/agent-runtime`. ## 2026-10-09 — one log for OC++ and the runtime (Phases 1 and 2)

- **Specter's Event Log in OC++'s database.** An OC++ adapter (`core/src/specter/event-log.ts`) implements the Event Log on OC++'s SQLite with two tables. Its append runs a host hook inside the transaction, where the Bus projects the commit, so Specter's log and OC++'s read models never disagree. The hook returns what to run once the transaction commits (notifying listeners). That work runs uninterruptibly with the append, and only the notifying part may be interrupted, as for a publish.
- **Two writers lose compare-and-swap races.** Core appended with compare-and-swap against the version it read and failed on a stale append, so a Command lost whenever another writer (the Bus's fact recorder, or another Session's Command) committed in between. Core now re-decides such a Command, up to 32 times, when the caller passed no `expectedVersion`. Fixing this in core instead of in each host is what the Command-consistency contract already implied: the runtime's own compare-and-swap is an implementation detail.
- **Listeners need each Session's events in order.** The Bus serializes publishes per aggregate with a lock held through notification. Runtime appends bypass `publish`, so the log handed to the runtime takes the locks of the Sessions its drafts name, sorted, around the append.
- **Message IDs.** With a persistent log, the runtime's default `msg_<session>_<ordinal>` is unique and stable across restarts, which a retried step needs. The per-boot prefix is gone. OC++ orders messages by sequence; clients sort by creation time and use the ID only to break ties.
- **Consolidating the catalog cost less than expected.** Every fold that applied OC++'s pairs (started/ended, success/failed) now applies one fact. Scenarios that pinned OC++'s projector quirks (an `ended` without a `started`, `text.ended` setting the latest block) lost the facts that described them and were removed. The merged Commands (`settleStep`, `settleToolCall`) are smaller than the ones they replace.
- **The runtime folds only its own catalog for execution facts.** A Session that OC++'s native runner ran records OC++'s vocabulary, which the runtime's folds do not read. This branch is unreleased and the native runner goes away, so no fold reads both.

## 2026-10-09 — the runtime drives OC++'s real steps (Phase 3)

- **Porting the runner's scenarios was the specification.** OC++'s 179 runner scenarios now run on the runtime's fixture, unchanged where the behavior is the same. Each place a scenario had to change records a deliberate difference (see the plan). They surfaced rules the runtime had wrong:
  - **Steering order.** A queued control item must never hold back a steer.
  - **Entry boundaries.** A continued turn, or a Session entering a new Location, delivers queued control items but not queued input.
  - **Wakes.** An execution claims the wakes recorded before it started. Without that, a failure that left input pending restarted the Session in a loop.
- **A Bus notification can interrupt a record.** OC++'s Bus notifies listeners interruptibly once a commit lands. When the attempt was stopped during that notification, the interruption escaped OC++'s uninterruptible step tail, so its interrupted tools and failed step were never recorded. Running each record in its own fiber, joined uninterruptibly, keeps a record whole once it begins.
- **Defects and failures are different budgets.** A failure to record retries the job; orphan reconciliation and the retry budget bound a step that keeps dying. Nothing bounded a delivery that kept dying, so a defect while delivering input now fails the execution.
- **Some facts only the host knows.** A dead attempt's tool calls carry what OC++ stored about them (a delegated child Session), which the log never saw. The `recover` hook lets the host settle those calls before the runtime settles the rest.
- **`step.streamed` became durable in OC++ on `main`.** The runtime records it as `session-step-streamed`, through an optional recorder method. The runtime's own model host does not record it.
- **Clock.** The step Plugin runs on the embedding's clock (`Clock.Clock` captured where the Plugin is built), so OC++'s TestClock drives retry delays.

## 2026-10-09 — external agents and restart continuity (Phase 4)

- **One more fact family bypassed the log.** OC++'s external agent records are durable events (`session.external.*`), defined outside `SessionEvent`. Adding them to the runtime's catalog and to the Bus's set of Session facts put every durable fact in Specter's log.
- **A Reaction per kind of execution.** An external agent's execution is a single host-driven job, not a sequence of steps. A separate `driveExecution` Reaction keeps that apart from the step Reaction. It applies only execution starts and settlements and the driver's changes, so it runs once per start. Its request carries the execution's number, so a duplicate is recognisably stale. The step Reaction latches the driver when an execution starts, so the agent's own step facts never schedule runtime steps.
- **Two restart mechanisms raced.** OC++'s claim sweep resumed claimed Sessions at boot, and the runtime resumed the same executions by replaying its Reactions. The runtime always won: it finished the turn before the sweep's notice landed. Keeping one owner meant deleting the sweep, its claims and its budget. The runtime's per-step retry budget already bounds a turn that keeps dying.
- **What only the host can tell.** Whether an execution was started by the current process is host knowledge: OC++ tracks the executions its own appends started. An external agent needs a message to continue a resumed turn, so the host's drive wrapper publishes the restart notice for an execution it did not start.
- **Test doubles outlive the code they came from.** Restart and shell tests need an execution without the runtime. OC++'s former coordinator moved to a test fixture rather than staying in `src` for them.
- **Typecheck coverage.** The CLI type-checks core's sources under its own tsconfig, which lacked core's `effect` path mapping, so the runtime's types resolved to a second effect copy (97 errors). Mapping `effect` as core does fixed it.
